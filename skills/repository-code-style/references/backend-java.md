# 后端 Java：业务表达与兼容性

本文件包含本 skill 采纳的条件偏好及有条件的样本归纳。四个仓库的证据见各仓库资料；
这里不定义新的框架、代码格式或统一架构。当前指令、正确性和接口兼容性始终优先；
在这些前提下，仓库显式规范优先于本偏好，本偏好优先于邻近实现。只对本次新增
或修改的代码应用偏好，项目已有能力必须支持，不为此迁移未涉及的存量实现。

## 采纳的条件偏好

用户转述的 user-experience 回填服务 leader Review（非原始 reviewer 记录）为
“减少字段硬编码”“可以尝试封装对象”。案例的修正差异见 UE-R1；本 skill 采纳
下列偏好，其跨仓库适用范围由本文件限定，并非 leader 发布的全团队统一规范。
使用时无需读取私人任务记录或作者的用户级配置：

- 减少 service 中硬编码的数据库列名和重复业务字面量；优先类型安全的查询、已有
  常量/枚举，或封装映射和计数的小对象。
- 重构时保持外部响应键与持久化业务映射，调整其内部表达。

这两条不意味着删除所有字面量、禁用 Map，或为每组字段新增 DTO。

## J1. 按字面量的职责选择表达

| 类型 | 首选处理 | 需要保留的边界 |
| --- | --- | --- |
| 持久化列名 | 有实体映射且项目支持时，沿用类型安全查询或现有 DAO | SQL、投影、连接查询等允许按项目惯例使用列名，不机械改写 |
| 产品线、状态、类型码 | 复用已存在的枚举或类型化常量 | 对照原数值、空值和未知值语义，不能靠名字猜映射 |
| 别名到业务值的映射 | 复用已确认的映射；必要时用局部映射对象集中解析 | 不修改存量数值、别名、清理规则或持久化含义 |
| 协议/JSON 字段 | 保留协议名，在已有 DTO、序列化注解或边界转换中表达 | 将 Map 改对象可能改变字段名、数字类型、空值和序列化 |
| 批大小、限额等业务阈值 | 复用已有配置/常量；稳定局部阈值可命名 | 不为一个固定值新增配置体系 |
| 展示文案、0/1 等局部算法值 | 依据所在模块的惯例与用途判断 | 不创建无语义的常量或多余的对象 |

“集中”必须有明确所有者和语义，不能仅改成一个汇集全仓库字符串的常量类。

## J2. 用对象表达共同变化的业务数据

适用信号：多个计数随同一个流程更新；稳定结果包含同一业务职责的字段；同一映射
的别名、归一化和解析分散在流程里。优先复用现有对象；没有合适对象时，按附近
代码选择小的内部类、结果对象或领域值对象。统计或映射对象内聚对应的更新/解析
职责；只负责传递稳定结果的 DTO 可以仅含字段与访问方法，沿用附近实现。

单个临时字段、短小边界 Map 或一次简单转换，不足以要求新增 DTO、接口或工厂。
Map 是否合适取决于数据职责，不根据容器类型直接判错。

## J3. 复用目标模块的职责边界

根据实际代码区分 controller/application、domain、DAO、外部 client 等职责。
查当前模块接口及调用方，不以另一仓库的目录名决定放置位置。先复用已有的
converter、client、DAO、枚举和工具；避免 controller 内新写一份已存在的业务判断。

按实际注解/接口/发布与注册链跨生产源码检索同机制实现，再选目录和范例。例如
Spring 事务监听与旧 EventBus handler 不是同一条链；存在前者时不能仅凭“都是
事件”或旧架构描述选择后者的包。对多个同名 Service 角色同样先辨明机制和职责。

沿相关生产链路核对下列能力的实际所有者，不把层名当成已经完成分层的证据：

| 能力 | 核对内容 |
| --- | --- |
| Controller / Feign 入口 | 按本模块当前规范处理传输响应包装；Service 是否只返回业务结果/抛既有业务异常，还是有明确兼容约定；不能拿旧接口透传作为新模块的充分依据 |
| Service / application | 业务决策、校验和跨能力编排/事务；持久化条件、纯字段映射、远程协议和配置解析是否有更合适的既有所有者 |
| Event / Listener / 共享类型 | 先查注解、发布及注册链，再选同机制目录和包依赖；不要按功能名统塞 Service，公共异常/结果类型不能随意反向依赖具体实现 |
| DAO / Mapper | 已有具名查询、关系替换、条件更新能力；查询条件与影响行数语义是否封装在持久化边界，业务合法性不下沉为 DAO 决策 |
| Wrapper / converter | 纯转换与所需数据由谁准备；不在字段转换时偷偷查库/远程调用，不复制同形 DTO 或制造万能转换器 |
| ACL / client | 远程协议、响应拆包、业务错误与未知异常的适配；只继承 Feign 接口不证明适配已经完成 |
| 工具 / 配置 / starter | 已有库函数、配置解析入口和框架扩展机制；比较输入语义、默认值及配置所有权，避免重复算法或重建全局配置来增加局部能力 |

这些是核对问题，不是跨仓库强制架构。单调用方、字段数少、类名叫 Context 等不能
单独证明应删除；已有重复对象和薄转发也不能因为能解释就保留。先查实际生产/框架
用途和职责，再比较直接调用、局部方法、已有对象与独立类的成本。

选择循环、stream、builder、setter、注入注解、内部类或独立类时，以邻近同类实现
为依据。本轮证据不足以设定这些写法的跨仓库统一偏好。

复用能力按[仓库探索步骤](repository-profile.md#1-先确定探索范围)核实具体 API、
有效依赖版本、真实调用方及所有者。集合比较要区分换序、重复、遗漏与空值，版本
比较器不自动等于严格格式校验，默认值/请求来源和线程生命周期不同也不能视为
等价。必要时用最小正反例验证；不能仅用工具名相同或编译成功判定替换完成。

## J4. 不把异常与日志缺陷复制成惯例

检查当前模块的错误返回、日志上下文和异常策略。补充必要业务标识，保持任务要求
的容错/传播行为；不因历史样本有空 catch、弱日志或 catch Exception 就照搬。
已有的异常缺陷单独指出，只有在本次授权范围内才修改。

涉及失败诊断、异步和框架扩展时，另追“谁在何时执行/抛错”：提交被拒绝与任务
执行失败、事务提交前后、失败标记再次写库、已有 Bean 被覆盖与追加插件、批量调用
返回 true 与逐行命中必须分别验证。先查已声明的依赖/运行版本，不把注解、catch、
编译或风格 PASS 当成运行时证明；未验证的机制风险单列，不隐含批准行为变化。

## J5. 风格重构也要核对行为

按受影响面核对：字段名、序列化注解、空值是否输出、Long/int 等类型、时间单位、
枚举 code、别名、顺序、去重、计数、分页游标、dry-run 和写入条件。

例如回填结果封装后，应保持原来的“扫描数量”口径；跳过或失败的行仍按原位置推进
游标。类型安全查询应保持筛选、排序和边界条件。若只是重构且行为相同，不偷偷
修正业务口径；发现问题时按任务范围处理并说明。

## J6. 业务说明要完整且与实现一致

检查本次涉及的公共契约和非直观政策是否按需说明职责、参数/输入、结果、失败与
副作用、关键约束；枚举、业务码和保留值的描述要与存储/对外含义一致。查询详情、
可用性校验和诊断回写等职责不能因字段相似混写成相同说明。

重构后回读文档：若容错从方法内部移到调用方，不能仍声称“本方法不会抛出”；
新增枚举描述不能顺手改变持久化 code。接口已有准确说明时不要求每个 override
重复粘贴，不为简单 getter 增加套话；注释冲突先查真实链路和需求，不按过时注释
擅改正确行为。局部普通字符串的表达约定也不能扩为 JSON、SQL 或协议字面量的
全局替换规则。
