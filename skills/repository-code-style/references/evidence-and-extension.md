# 证据维护与平台扩展

## 当前结构选择

保留一个 `repository-code-style`：选同类范例、实施和 diff 自审适用于不同平台。
将领域和仓库惯例放在按需读取的 reference 中，避免多个 skill 重复定义流程与优先级。
只有平台新增了独立输入、工具、操作步骤或交付要求，且主入口路由难以保持简洁时，
才拆出独立 skill；拆分后保留共同的本地范例选择原则。

当前已研究后端 Java，以及 community/mweb 的 C 端 H5 和 internal-ad 的 B 端 Web。
客户端已补充 RN、Android、iOS、HarmonyOS 的各端资料；没有提供的规则保持未定义。
同名作者先确认账号/邮箱，不把模糊匹配合并为身份。重复 cherry-pick 不作为独立
证据；AI co-author 和生成绑定的实际业务修正明确标注，不能代表个人长期手写风格。

## 新规则的取样方法

1. 核对仓库路径、当前 branch/HEAD、目标模块规范及现有工作区改动。发现
   AGENTS.md、CLAUDE.md、.cursorrules、.cursor/rules/ 等适用规则及检查器配置，
   用 `git ls-files`、必要时 `git check-ignore` 区分团队跟踪文件与个人配置。
2. 用 `git log --all --no-merges --author='<已确认作者邮箱>' -- <模块路径>`
   找代表性提交。作者匹配采用邮箱，避免显示名别名影响结果；发现不完整匹配再确认身份。
3. 选业务实现、对象封装、查询、修正提交；排除合并和纯机械改动。生成文件只取
   可核实的业务修正差异，不将生成结构或整份文件归因作者。
   为正例查 `git show <commit> -- <file>`，再查相关定义、调用方和后续修正。
4. 比较同职责代码的相同点和差异，主动找反例。单份提交能证明一次选择，不能证明
   全仓库惯例；某个作者的新增行不代表所在整份文件或所有项目。
5. 按适用范围写规则，附下列字段；并用未参与提炼的任务检查能否帮助实际实现。

```text
ID:
规则与适用条件:
证据类别: 显式规范 / 转述反馈 / skill 条件偏好 / 样本归纳 / 待确认假设
来源: 已包含必要上下文的 Review 转述，或仓库 + commit + 文件 + 方法/符号
已观察事实:
可采用的写法:
反例、不适用条件及契约风险:
验证方式:
取样日期与本地 checkout 范围:
```

**显式规范**记录其跟踪状态、适用条件和强制/推荐级别；**转述反馈**不是已核实
的原始 Review，只在已确认的范围内应用。**skill 条件偏好**写清跨模块适用前提，
不能冒充 leader 全团队规范。**样本归纳**只能在相同条件下采用，多个独立样本
支持后再考虑推广。**待确认假设**不作为提交门槛。
不要将自己生成的修正标成 leader 的代码或已批准范例。

## 更新、检查与验证

- 业务仓库当前规范和实现变化后重新核对样本。先修正相应 reference，必要时
  再调整主流程；同步 version、CHANGELOG、根 README 的版本和验证记录。
- 能稳定判定的格式/静态规则优先使用仓库已有检查器。新增检查器或规则配置应是
  单独的、可审查的仓库改动；不要以正则把所有字符串、Map 或数字判成风格违规。
- 用历史 Review 作回归案例，用未参与提炼的任务作保留场景。相同输入比较有/无
  skill 的产物、证据选择、契约保持及过度抽象。由 reviewer 判断主观风格项。
- 保留基线和使用 skill 后的证据，标出未运行项。若基线本已符合规则，不能宣称
  skill 改善了结果。合成场景通过不等于在真实仓库或 leader Review 中已验证有效。
