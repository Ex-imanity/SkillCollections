# 仓库探索与本地风格档案

本档案保存可复核的源码定位和适用判断，让后续任务复用探索结果；它不是新团队规范，
也不替代当前源码、明确指令或人工 CR。不要把业务代码、内部接口、凭据或评估输出
写入 Skill 分发包。模板见 [local-style-profile.template.md](../assets/local-style-profile.template.md)。

## 1. 先确定探索范围

记录仓库身份、分支、HEAD、比较基准、工作区已有改动、日期和目标模块。读取适用
规范与活动文档入口，再追一次最贴近需求的生产调用链：入口 → 业务编排 → 数据/外部
能力 → 结果转换/返回；有事件/异步/客户端生命周期时，追加注册和执行链。

选择范例前先识别目标类型的注解、继承/实现、发布者和扫描/注册机制，再跨目标
仓库的生产源码检索这些机制标记的定义及调用。先筛出同机制候选，再比较职责、
目录和实质时间；不能只搜索目标功能目录或按 Event、Listener、Service 等类名找。
例如 Spring 事务监听器应先查同类注解与发布链，不能找到一套旧 EventBus 目录就
停止，也不能只按架构文档中的“事件目录”搬文件。对公开入口/注册类型先核对
框架可达性；有更贴近的同机制实现却未查看，该维度不能判为已验证。

先形成三项可使用的结论，而不是仅列读过哪些文件：

| 内容 | 必须回答 |
| --- | --- |
| 组织与职责图 | 现有模块、目录、包/导出和依赖方向；每层输入/输出及不承担什么；机制身份、跨生产源码发现的同机制候选和最终落点 |
| 已有能力清单 | 当前任务可能复用的工具、查询、转换、异常、配置解析、客户端、框架扩展点；真实调用方、输入限制、默认值和所有者 |
| 本次文件落点计划 | 每个拟新增/移动的类或文件的职责、目录、现有范例、实际生产入口；复用/合并/保留独立类的理由 |

范围由任务决定，不要求浏览全部业务。改一个方法只补相关链路；新增模块、跨层
重构、已有 CR 漏检后，必须覆盖完整相关链路。找不到同职责实现时记录检索范围和
设计依据，不能虚构仓库惯例，也不因为缺专属 profile 就停下所有可做工作。

能力清单不能停在库名或候选列表。对本次实际采用/替换的能力，核实真实符号
（Java 为 FQN、方法及签名）、有效依赖/运行版本、生产调用方，以及静态/实例、
可见性、Bean/配置所有者和生命周期。记录相关输入来源/优先级、空值、非法值、
默认值、顺序/重复和失败语义，不为无关维度填表。对照实际 API/源码及必要的最小
正反例，给出采用或排除依据；声明版本不能直接代替实际解析版本。

例如重排允许 `[1,2]` 与 `[2,1]`，但拒绝重复的 `[1,1]`；列表直接相等或先转 Set
都不能独自证明等价。请求来源/默认值、线程生命周期不同的同名工具也不能直接
合并。按任务需要区分权限、审计、防抖、内容去重、限流和幂等，不能以“用了 Redis”
替代能力核对。无法确认时保留该替换的未验证状态，不贸然改写或判其风格通过；
继续完成其他有依据的部分，不要求研究全仓所有依赖。

## 2. 选当前有效的范例

1. 以任务中的当前日期计算约六个月窗口，优先在适用分支/比较基准的相关路径中找
   实质改动。可用 `git log --since=<起始日期> --no-merges <适用ref> -- <相关路径>`。
   不默认用 `--all` 把未采用的旁支当规范，不为取样擅自切分支或更新远端。
2. 看完整相关方法与 `git show` 差异，记录 commit、实质改动日期、当前是否仍存在、
   适用职责。文件最后修改时间、近期 import/注释/格式提交不能证明设计是近期选择。
3. 遇到旧新写法并存，至少比较冲突双方和后续修正。先遵守当前明确要求及适用规范；
   历史描述过时与强制指令冲突应分别判断，不能用代码存在推翻明确要求。人工 CR
   记录其来源、适用范围、落地状态；“建议”不自动升级为强制要求。
4. 排除已回滚、纯生成/机械改动以及本批未验证实现互证。刚提交/合并的 AI 代码
   不因时间新就变成团队惯例；已确认的人工 CR 修正可以作为该范围的修正依据，
   但不能用同一批类自证全仓规范。
5. 六个月是检索优先级，不是旧代码失效期限。长期未变但仍被当前生产链路采用的
   目录或工具可以保留，注明近期搜索结果、回退原因和现状核对。无可用历史时使用
   当前明确规范和真实实现，限定证据强度；不虚构“已查看近期提交”。

不要把“代码曾存在”“作者相同”“只有一个调用方”“Service 都应该如何”作为
充分依据。抽象和职责的判断要能同时解释采用和不采用的候选，防止为已有草案挑证据。

## 3. 本地保存和增量维护

- 优先复用仓库已有的本地维护位置；没有约定时使用仓库根的
  `.repository-code-style/profile.md`，大仓按模块拆文件，由 profile 索引。
- 从模板生成时填入当前可访问的 Skill 来源/根目录；模板中的 reference 名称相对
  Skill 根目录，不是本地档案目录。跨 agent 分享时改为对方可读定位或最小摘录。
- 写入前验证忽略边界。Git 仓库可先用 `git check-ignore`，未忽略时通过
  `git rev-parse --git-path info/exclude` 定位本地排除文件，幂等加入
  `/.repository-code-style/`。不要为保存私人档案修改已跟踪的 `.gitignore`、规则文件
  或安装目录，也不要自动取消跟踪已有文件；发现目标已跟踪，改用已忽略的位置。
- 忽略是本机版本控制边界，不是脱敏。仅保存必要代码定位、短结论和约束，不保存
  凭据/真实用户数据，不把私有档案直接复制进评审请求或公开文档。
- 跨任务复用前核对仓库、模块、比较基准、上次验证 HEAD 与当前相关差异，包括
  staged、unstaged 和 untracked 源码。HEAD 未变不代表工作区没变；mtime 或
  “最近生成过”也不能代替检查。无关提交只记录重新核对，不必重扫全仓。
- 相关目录迁移、工具/配置所有权变动、新 CR、版本/依赖升级、分支/基准变化会使
  对应条目失效：先复查再更新受影响项。过时结论标为 superseded，留下替代依据，
  不继续把旧条目当规则，也不静默删掉其冲突来源。
- 非 Git 项目使用现有本地资料位置并注明缺少提交历史；未落实共享前保持本地。
  reviewer 读不到本地档案时自行重建需要的依据，不因缓存缺失直接判代码有错。

## 4. 实施与 Review 如何消费

实施前给本次任务留下具体记录：采用哪些档案条目、刚核对到什么版本、哪些文件
放在哪里、复用什么能力、保留什么契约、哪些缺口/偏离需要解释。没有本次范围的
组织/职责/复用依据时先补探索，不先写完再编造前置记录。

Review 先从实际改动重建文件清单、职责图和入口，独立核对档案与源码。先判断类/层
的必要性、包归属、依赖和已有能力，再看内部实现。只解释一处注解正确，不能证明
整个 DTO 有用途；需要保留请求值，也不能证明重复 Context/Resolver 必须保留。

对跨 agent 的交接提供可访问的最小档案摘录或相对定位、比较基准、文件落点和冲突
记录。档案不可读时，在已授权分享范围内内联：关键类型的机制身份（注解/接口/
注册方式）、最近似同机制生产范例的路径 + 符号 + commit，以及相关能力/配置
所有者；同时注明仓库、范围和基准。无法提供的字段标明缺口，由 reviewer 补查，
不直接复制整份私有档案。审查者核实近期范例及旧样本回退理由；缺字段先补查，
不把文档齐全等同于语义正确。最终按角色契约给出风格状态，单列机制验证和未核实范围。
