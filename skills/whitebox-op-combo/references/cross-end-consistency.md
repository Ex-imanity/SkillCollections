# 跨端一致性分析

## 1. 触发和范围

用户提供两端及以上的代码或分支时，默认建立行为对照，不等用户另提“一致性”。只有一端时按普通白盒流程工作，不强制补齐三端资料或空矩阵。
对照围绕同一业务对象、动作和用户结果，平台列按实际范围增删。代码缺失为“未核实”，产品明确排除的端才是“不适用”；搜索未找到入口不能证明不支持。

阶段 0 先承接已有差异记录。旧结论是检索线索，各端提交不同时逐条复核；不能用旧 SHA 宣称新提交仍有问题或已经修复。

## 2. 可比条件

每端记录仓库、分支、SHA、读取时间；有实测时另记构建、设备、系统和验证时间。对齐以下业务前置，再判断差异：

- 同一对象/账号状态、权限、实验/配置、缓存、生命周期和异步时机。
- 语义等价输入及其平台适配；不同端的合法解码类型可以不同，不能因为 JSON 字节不同就定缺陷。
- 各端自己的发布门槛及开关，而非要求版本数字相同；例如 Android 10.2→10.3 与 iOS 4.7→4.8 都可命中升级，仍须核对共享规则和客户端逻辑。

未知配置或不可见代码保持未知，不借用另一端补齐。前置不同先写“条件不可直接比较”，列出需要对齐或允许适配的项，不将配置差异定为实现 bug。

## 3. 单动作和流程对照

阶段 1–2 建立业务行为与端内原子/入口的映射，检查以下风险维度；不穷举无关文案：

| 维度 | 代码中要核对的路径 |
|---|---|
| 入口和能力 | 显示/禁用条件、权限、版本门槛、入口缺失与不可见边界 |
| 空值和失败 | 空正文/默认值、请求失败、超时和降级后可用能力 |
| 退出与恢复 | 确认、遮罩/返回关闭、重进、刷新及持久化 |
| 异步和中断 | 请求先后、重复触发、回调取消、后台和页面销毁 |
| 共享入口编排 | 相邻提示/流程的优先级、互斥、等待、并行与后续请求 |

从当前入口沿可见调用链追相邻流程，即使它属于另一个功能 slug；记录范围外或不可见的后续节点。把影响范围对象的读写/时序动作放入原子审阅；纯语义差异另列行为对照，不为通过脚本硬造读写点。

原子表确认后，在阶段 3–4 做单动作对照和共享入口流程推演。`represented_by` 只折叠组合计算，`ends` 仅为说明，脚本低分/剪枝不免除语义检查。相同读写集也可能有不同默认值、退出方式或请求时机。

同一个端内流程分别推演；跨设备只在共享账号/房间/对象及可达事件上建模，不能把 Android 的本地确认后面直接接 iOS 的本地回调当作同一设备流程。

## 4. 证据与标准状态

每个行为 ID 记录四类独立信息：

| 信息 | 填写规则 |
|---|---|
| 覆盖状态 | 一致 / 有差异 / 未核实 / 不适用；限定具体路径和比较条件 |
| 每端证据 | 行为、文件:行号及固定 SHA；代码证实、待运行验证、实测验证可分别记录，静态因果与运行结果不互相替代 |
| 标准决策 | 待确定 / 允许差异 / 需统一 / 已确定，附来源、日期、适用端和例外；“需统一”不表示已选定具体行为 |
| 契约判断 | 已知契约及违约证据，或“契约未知，暂不判缺陷”；旧缺陷状态映射见 [verification.md](verification.md) §1 |

“代码证实差异”不等于“产品确认 bug”；实测复现差异也不自动给出标准。契约未知时只进差异矩阵，不套缺陷状态或缺陷等级。三端一致也不能反证实现正确。

## 5. 候选标准与决策

待确定项写出用户影响、至少两个可行候选、推荐方案及理由、影响端和验证代价。可以采用某端方案、新统一方案或合理的平台例外；按用户结果和业务不变量比较，不要求底层实现相同。

例如 Android 空通知不弹、iOS 用默认正文弹：两者都只是候选。比较信息是否必须触达、空配置如何兜底、是否阻断主流程，再给建议；不能默认 Android、iOS 或多数端为标准。

产品/设计/技术文档冲突时列出各来源及冲突点，保留本轮明确选择，未解决的继续待确定。标准选择不新增阻塞全部工作的检查点：继续独立分析；待定预期留在对照文件，不进入可写回的确定性通过/失败用例。

## 6. 用例回流

单 slug 的对照文件为 `whitebox-output/{slug}/cross-end-consistency.md`；多 slug 用用户指定的批次目录，未指定则生成本次唯一 batch slug：`whitebox-output/{batch}/cross-end-consistency.md`，子功能在批次内。不要复用裸 `whitebox-output/` 存放不相关任务的决定。

行为 ID 为 `{slug}.{behavior}`，批次内唯一；跨 slug 共享行为以首次引入该行为的 slug 为前缀，后续引用保留该 ID。共用的决定只维护一份，各功能 atoms/analysis/cases 以相对链接和行为 ID 反向定位。前期功能用例能修改时也加反向定位；权限或格式不允许时在对照文件登记待同步位置。

标准确定后逐项：

1. 记录决定原话/来源、日期、适用端及允许例外，更新对照表和候选预期。
2. 更新 `analysis.md` 的契约判断和正文、`cases.md` 的确定预期及备注；仅获授权时同步前期 `full.md` 或外部用例，否则列具体章节/用例及待同步内容。
3. 分开记录“决定已定 / 文档已同步 / 代码已修改 / 已复测”。代码更新后按新 SHA 复核，不把决定当作修复证据。

只接收已有分析的决定并给回流建议时，不重新建立原子审阅门槛；若增加动作或重做组合分析，仍需按主流程审阅原子表。既有原子审阅是唯一必做人工门槛。

## 7. 边界示例

- **共享入口**：Android 通知与房间请求并行，iOS 关闭通知后请求；两端设备冲突均优先于继续学习。分别记录有差异和一致路径。代码能证明并行，实际弹窗遮挡要设备验证。
- **已定标准**：用户决定“通知完全关闭后请求配置，冲突优先于继续学习”。将同一决定关联通知与房间入口两 slug；更新两端建议预期及旧功能用例，未给新代码则不能写“已修复”。
- **合法适配**：历史时间字段 number/string 分端解码到同一语义，不因类型不同定 bug；缺鸿蒙代码时标未核实，不能写“不支持”。

模板见 [output-templates.md](output-templates.md) 的跨端一致性对照部分。只改分析和获授权的用例，不自动修改业务实现、安装 Skill 或写回平台。
