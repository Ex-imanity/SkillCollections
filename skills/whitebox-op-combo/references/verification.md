# 验证、定级与归属

静态分析的产物是假设。开发会不会认一条结论，取决于这一步做得够不够：
**状态标记清楚、复现方法能照着做、定级有依据、归属不含糊、测试能快速判定。**

## 1. 状态标记

每条发现的标题都带一个标记：

| 标记 | 含义 | 要求 |
|---|---|---|
| 【已确认】 | 代码里能直接读到因果链，不依赖运行期数据 | 引用到 `文件:行号`，贴关键代码片段 |
| 【已确认·潜在】 | 代码缺陷确定存在，但当前业务数据/配置下尚未触发 | 写明触发条件（"一旦某迭代往 extData 加新键"） |
| 【潜在】 | 取决于运行期时序、配置值或黑盒服务的行为 | 写明需要什么证据才能升级为已确认 |
| 【已排除】 | 看似有问题，查证后不成立 | 写明是被哪一层兜住的；可以只作为某条发现里的一段，不必单列章节 |
| 【已实测复现】 | 测试执行后追加，替换或补充在上述标记后 | 注明端、分支、复现步骤与抓包证据位置 |

标记要随事实更新：用户或测试反馈后，**直接改成最新结论**，不要在正文里保留"之前判断为……后来发现……"的历史叙述。
读者要的是结论，不是推理过程的考古。

## 2. 复现方法

每条已确认 / 潜在发现都给一段可以照着做的复现：

- **前置**：账号状态、实验命中、开关值、需要的数据（带图 / 单题 / 多卡片回答）；
- **步骤**：精确到接口和字段，写出操作之间的**时间要求**（"回答结束后 1 秒内点赞""停留超过 5 分钟"）——异步窗口和 TTL 类问题没有时间要求就测不出来；
- **判定**：看哪个接口的哪个字段，而不是"看页面是否正常"。

**先想清楚复现要多复杂。** 如果一条发现需要"精确卡在毫秒级窗口内 + 特定配置 + 特定数据"才能触发，
而又没有别的更常见的触发路径（例如落库失败、被其他写入覆盖），就应当**降级**，并在定级依据里说明。
反过来，如果找到了一条日常操作就能撞上的路径，要把这条路径作为主复现写在最前面。

## 3. 定级

按"用户撞上的概率 × 撞上后的后果"定，而不是按代码缺陷本身的严重程度：

| 级别 | 典型条件 |
|---|---|
| **P0** | 日常操作路径可达（先看完、退出、再回来操作），产生**静默错误数据**（错题本存错答案、赞挂错对象），或核心内容丢失 |
| **P1** | 需要特定但合理的操作序列 / 时机（中途退出、跨题型重生），或后果可见但可恢复 |
| **P2** | 需要窄时间窗口、特定配置或非常规操作；或当前自洽、只在未来迭代中才会暴露（【已确认·潜在】） |

定级依据写成一句话放在优先级表里，例如："已实测复现：重生后入口按预期回到可加入态，用户再加一次存的仍是旧答案；用户完全无从察觉"。
**"静默"是加分项**：页面上有异常提示的问题用户会反馈，静默的数据错误只能靠测试发现。

## 4. 归属：服务端还是客户端

开发拿到结论的第一个问题是"谁来改"。每条发现都要回答，并给出依据：

判定顺序：

1. **数据在哪一层第一次变错？** 服务端落库时就错了 → 服务端；服务端数据正确、客户端合并/渲染时错了 → 客户端。
2. **客户端有没有能力发现数据是错的？** 字段没有版本号、时间戳、来源标识时，客户端只能照单全收 → 客户端无责。
3. **三端行为是否一致？** 三端完全一致通常说明它们在忠实执行同一份服务端契约；只有一端出错，大概率是该端实现问题。
4. **修复点在哪？** 找到最小修复点并写出来（"UpdateHisMessageCmd 增加一个 getter + peek 里补一行 set"）。修复面小是推动修复最有力的论据。

两个反模式：

- **不要给客户端提 workaround 来掩盖服务端写漏**（例如"客户端比对两个字段，不一致就禁用入口"）。这会把一个服务端缺陷变成三端各写一遍的兜底逻辑。
- **契约本身缺失时，归属写"协议"**：例如"回答是否完整"这个状态在存储和接口里都不存在——既不是服务端写错了也不是客户端读错了，需要双方一起补字段。

## 5. 快速指纹

为每条发现找一个**不走完全部流程就能判定是否命中**的信号，写进 analysis.md 和对应用例的执行步骤里：

- **同源字段比对**：两个字段本应来自同一数据源（例如回答正文和错题本快照里的答案正文都来自同一缓冲区），在同一个接口响应里比对是否一致；
- **计数比对**：同一 questionId 下的卡片数、同一题的错题本记录数；
- **存储直查**：Redis / HBase 里该字段的值与接口返回是否一致（适合异步窗口类问题）。

指纹让测试执行从"走到最后一步看页面"变成"抓一次包看两个字段"，也让回归时可以批量扫描。

## 6. 回流

测试执行后把结果回填：

- 复现了 → 标记追加【已实测复现】，补证据位置；
- 没复现 → 查是用例前置没满足（开关、实验、时间要求），还是分析错了；分析错了就改成【已排除】并写明原因；
- 测试中发现了分析没覆盖的问题 → 回到原子表，看是漏了原子、漏了读写点，还是漏了模式；**补的是方法的缺口，不只是这一条用例**。
