# 产物模板

所有产物落在 `whitebox-output/{slug}/`（用户指定了目录则用用户的）：

```
whitebox-output/{slug}/
├── baseline.md     ← 阶段 0：范围对象、仓库/分支/提交、配置来源、盲区
├── atoms.json      ← 阶段 1–2：读写点与原子（脚本输入，机器可读）
├── atoms.md        ← 阶段 2：原子表（人审阅用，HITL 检查点）
├── pairs.md        ← 阶段 3：op_matrix.py 输出，不手改
├── analysis.md     ← 阶段 4–5：缺陷分析
└── cases.md        ← 阶段 6：测试用例（兼容 case-lite full.md 格式）
```

多端任务增加下文 `cross-end-consistency.md`。单 slug 用原目录，多 slug 的批次根及链接按 [cross-end-consistency.md](cross-end-consistency.md) §6；以下各功能模板放在相应子目录。

## atoms.md

原子、读写点与 atoms.json 对应。对象关系与动作绑定记录在原子表中，供审阅和后续组合核对。

```markdown
# {功能} —— 原子动作表

范围对象：{业务对象及区分实例的条件}

## 对象与资源

| 对象或资源 | 业务身份 / 应有归属 | 实际定位 / 层 / 共享范围 | 关系及代码证据 |
|---|---|---|---|
| {对象 A} | {实例键及版本} | {记录、缓存或内存实例} | {与关联对象或快照的关系，文件:行号} |
| {共享资源 S} | {服务于哪些对象} | {实际键或槽位，作用范围} | {读写入口证据，未知项注明待核实} |

## 原子动作

| ID | 动作 | 入口 | 写 | 读 | 来源 | 端差异 | 备注 |
|---|---|---|---|---|---|---|---|
| A0 | 带图提问 | mainSearch（SSE） | 回答正文、错题本快照、兄弟卡片、重生缓存、端内存 | — | 代码 / 需求 | — | 创建动作；阶段：深度思考中 / 正文中 |
| A2 | 重新生成 | mainSearch + regenerate | 正文、extData.mistakeBook、兄弟卡片、端内存 | 重生缓存、HBase 记录 | 代码 / 需求 | iOS 请求体不带 agentType | 替换回答；A2b 跳过深度思考由它代表 |

## 动作绑定

默认绑定：{简单场景可在此写共用目标、读写资源及前置，表中补各动作的差异}

| 原子 ID | 目标 / 读写点或资源 | 前置 → 完成后状态 | 异步发起绑定、完成目标及守卫 |
|---|---|---|---|
| {A1} | {对象 A 或集合及其成员范围，引用读写点或资源} | {入口状态 → 结果} | {绑定 A，完成时核对是否仍为 A 及版本，附证据} |

## 隐式动作清单

| 动作 | 结论 |
|---|---|
| 退出页面再重进 | A3 |
| 切后台再回前台 | 不适用：{理由} |

## 覆盖检查结果

（粘贴 pairs.md 第 1 节的结论：孤儿写入点 / 孤儿读取点 / 空原子 / 替换漏写字段，每条都要有处理结论）

## 盲区

- {看不见代码的服务、无法确认的配置值}

## 业务语义和跨端映射（多端时）

| 行为 ID | 端 / 原子 ID / 代表 | 入口及语义变体 | 共享入口相邻动作 | 对照位置 |
|---|---|---|---|---|

同读写集折叠不删除语义变体；对照位置使用相对链接和行为 ID。

## 请确认

1. 有没有代码之外的动作（后台、客服、其他系统、另一个角色）？
2. 有没有用户实际上不会做的原子？（会降级，不会删除）
3. 有没有应该拆开的变体，或对象归属、共享资源和作用范围需要纠正？
```

## analysis.md

```markdown
# {功能} —— 代码问题分析

## 0. 分析基线

| 仓库 | 分支 | 最新提交 |
|---|---|---|

下文结论限定上述提交。旧状态含义与契约要求见 verification.md §1，代码证实、实测和标准决定分别记录；契约未知的差异不作为已确认缺陷。
盲区：{黑盒服务、未知配置}

跨端对照：{多端时填写相对链接与行为 ID；单端不强填}

## 组合核对

| 组合及绑定 | 来源 | 触发入口 / 可达条件 | 实际资源关系与证据 | 处理及依据 |
|---|---|---|---|---|
| {A6(表 A) → A6(表 B) → 渲染 A} | {矩阵或矩阵外候选} | {同进程，B 在 A 读取交接槽前写入} | {两张表共享交接槽，引用原子表和代码} | {按 atomization §2.3 选择处理结论} |

保留推演项关联具体推演章节。守卫拦截项写明被阻止的步骤及守卫证据。待核实项关联「仍需确认」。暂缓项写出原因及恢复条件。

## 1. 【状态标记】{一句话说清楚：什么顺序 → 什么后果}

> 触发条件：{最常见的那条路径，一句话}

契约来源：{已确认的产品、设计或协议及其位置。待决定项记入仍需确认，多端关联跨端对照}
代码/运行证据：{固定 SHA 的因果链；设备/构建实测或待验证}
关联行为：{行为 ID 及相对链接}

{先排除看似会出问题但实际被兜住的路径（如有）}

{因果链：每一环引用 `文件:行号`，关键处贴代码片段}

{后果表：哪些字段停在什么状态、用户在哪里能感知}

### 1.x 归属结论（服务端 / 客户端 / 协议）
{判定依据 + 最小修复点}

### 1.x 快速指纹
{不走完全部流程就能判定的信号}

## N. 优先级建议

| 级别 | 问题 | 依据 |
|---|---|---|

## N+1. 根因收敛

上述问题收敛到 **K 个结构性成因**：
1. **{成因}** —— {说明}。§a §b 源于此。建议：{结构性修复方向}

## N+2. 仍需确认的问题

1. {问题} —— {需要谁、用什么证据回答}
```

写作约定：

- 每条发现的标题就是结论，读者只看标题也能知道问题是什么。
- 引用写 `文件:行号`；在能生成可点击链接的环境里用相对路径链接。
- 结论直接写最新的；用户纠正或测试反馈后改正文，不保留推理历史。
- 根因收敛是给架构/负责人看的：把 10+ 条具体问题收敛到 3–5 个成因（缺少统一的读改写契约、状态在存储里不存在、多端各自实现同一协议……）。

## cases.md

与 case-lite 的 `full.md` 格式兼容（编号即路径），可直接用 case-lite 的 `writeback.py` 写回搬山：

```markdown
# {功能} —— 操作组合测试用例

覆盖对象：{范围对象}

| 操作 | 简称 | 接口 |
|---|---|---|

**验证分支**：{同 analysis §0}

只将标准已确定的场景写成测试点。标准待定项留在 `analysis.md` 的「仍需确认」，多端关联跨端对照文件。当前实现预计不符已知契约时，以 `备注：` 关联 analysis.md 章节及决定来源。

**通用环境要求**：
- {实验、开关——写明开关为 false 时哪些用例会失效}
- {抓包需要留存的字段}

## 场景1：{A 与 B 的顺序组合}

### 测试点1.1：{A → B → C 后，{字段}应为{期望}}

#### 执行步骤
1. {在第一步写清前置。涉及多个实例或版本时，标记 A/B 或 v1/v2，并说明相关的账号、会话、设备或共享条件}
2. {说明操作针对的实例、先后顺序及等待条件}

#### 预期结果
1. {针对指定实例的 UI 断言}
2. {如适用，核对另一实例或共享资源的接口字段}

**更快的判定方式**：{快速指纹}

备注：{当前实现与预期不符的原因一句话}，见 analysis §N。
```

用例约定：

- **场景按"组合的原子对"组织**（点赞与重新生成的顺序组合、加入错题本与退出重进的组合），另设"并发与竞态""跨端一致性""中断"等横切场景。
- **预期结果写已知契约下的产品应有行为**，不凭现状选定标准。现状写在备注里并关联 analysis 章节及行为 ID。
- 每个测试点的步骤里写清**时间要求**和**端别**。
- 纯白盒、黑盒无法触发的边界（需要精确卡时序）单独成点，标题注明"白盒边界"。
- 不写优先级标记（与 case-lite 一致，由用户事后标注）。

## cross-end-consistency.md

只在多端分析时创建；平台列按实际范围增删，空白表格不算完成。状态填写规则、批次目录和 ID 唯一性见 [cross-end-consistency.md](cross-end-consistency.md)。

```markdown
# {功能或批次} —— 跨端一致性对照

## 范围与可比条件

| 端 | 仓库 / 分支 / SHA / 读取时间 | 构建 / 设备 / 验证时间 | 配置 / 账号 / 权限 / 缓存 / 时序 | 输入适配 / 未知项 |
|---|---|---|---|---|

## 行为对照

| 行为 ID | 前置与动作 | Android 行为与证据 | iOS 行为与证据 | Harmony 行为与证据 | 覆盖状态 | 每端证据状态 | 标准来源与决定 | 关联用例 |
|---|---|---|---|---|---|---|---|---|

## {slug.behavior}：差异详情与标准候选

- 用户影响、已排除的前置差异：{内容}
- 固定提交代码证据、待运行验证及验证方法：{分开填写}
- 契约判断：{已知契约及违约证据，或契约未知、暂不判缺陷}
- 候选：{至少两种可行行为、影响端与验证代价；标准已定则引用决定}
- 推荐与理由：{建议不等于已确定}
- 标准决定：{状态、原话/来源、日期、适用端、允许例外}

## 回流与未核实项

| 行为 ID | 决定及受影响端 | analysis / cases / 前期 full 的具体定位 | 已同步 / 待同步及原因 | 代码修改 / 新 SHA 复核 / 复测 |
|---|---|---|---|---|

各 slug 的 atoms/analysis/cases 以相对链接和行为 ID 反向定位此文件；无法更新的前期用例列出待同步项。
```

标准未知示例：`notice.empty-content` 对照“空正文不弹”与“本地默认正文弹”，两项均为候选，写明影响端、推荐理由和待确认；不把任一项放进确定性验收。

标准已定示例：用户选“通知完全关闭后请求房间配置，设备冲突优先于继续学习”。`notice.entry-order` 由通知和房间入口两个 slug 共用一份决定，回流两端预期及冲突优先用例；新代码未提供时仍记待复核。
