# 原子动作拆分与覆盖度

整个方法里最容易出问题的一步：原子动作拆漏了，后面的组合再完备也只是在一个残缺集合上穷举。
本文回答三个问题：**原子怎么定义、从哪里来、怎么证明没漏**。

## 1. 原子的定义：读写集等价类

**原子动作 = 对共享状态有独立读写集的一次用户可感知操作。** 判定只看读写集，不看 UI：

| 情况 | 处理 | 例子 |
|---|---|---|
| 两个 UI 动作读写集相同 | 合并为一个原子，另一个标 `represented_by` | 点赞 / 点踩走同一接口、写同一字段 |
| 一个 UI 动作因状态不同走出不同读写集 | 拆成多个原子（变体） | 重新生成：缓存命中 vs 缓存过期（后者读不到缓存、走降级路由） |
| 一个 UI 动作内部有多个阶段、每个阶段落盘状态不同 | 保留为一个原子，声明 `stages` | 流式输出：深度思考中 / 正文输出中 |
| 一个动作复用了另一个动作的写路径 | 两个都保留，并把复用的写入点同时挂到两者上 | 加入错题本的历史同步复用点赞的 update 接口 → 继承了"删兄弟卡片" |
| 不读写任何共享状态 | 不是原子，移出范围 | 纯展开/收起、复制文本 |

为什么以读写集为准：组合是否产生问题，只取决于两个动作是否碰到同一份状态。按 UI 拆会同时犯两种错——
把同一个动作拆成两个（组合数量翻倍，全是重复），又把一个动作的状态变体混成一个（漏掉真正会出问题的分支）。

## 2. 范围锚点：一个共享对象

一次分析只围绕**一个共享对象**，例如"同一 questionId 下的一条 AI 回答""同一张订单""同一次批改任务"。
这个对象决定了原子动作的边界：**凡是会读或写这个对象任一状态（服务端存储、缓存、客户端内存）的动作都在范围内，其余都不在。**

对象选得太大（"整个 AI 搜索"）→ 原子几十个、组合爆炸；选得太小（"点赞按钮"）→ 看不到跨动作的状态冲突。
经验上一个合适的对象对应 5–10 个原子、15–40 个读写点。

对象的状态要按**存储层**展开：服务端各存储层（Redis / HBase / MySQL / MQ 下游）、临时状态（带 TTL 的缓存、待处理队列）、
各端内存。同一字段在不同层是不同的读写点——绝大多数"异步窗口""层不对称"类缺陷都藏在这里。

## 3. 四个来源，三角互证

单一来源一定会漏。四个来源各自擅长发现一类原子：

| 来源 | 方向 | 能发现 | 会漏 |
|---|---|---|---|
| **代码枚举**（主来源） | 自底向上 | 所有真实存在的入口：页面上的点击回调、生命周期回调（`onDestroy` / `deinit` / `aboutToDisappear`）、SSE/推送回调、页面发起的每个接口 | 代码里没有、但产品要求有的动作（这本身就是缺陷） |
| **需求 / 设计稿** | 自顶向下 | 产品定义的全部交互，以及每个交互"应该"产生的效果 | 隐式动作、代码里额外长出来的入口 |
| **隐式动作清单** | 横切 | 非 UI 动作：退出重进、切后台、杀进程、断网、另一设备、登录态变化、时间流逝（TTL）、连点、中途打断、他人修改 | 业务特有的隐式动作 |
| **人** | 经验 | 代码外的动作：运营后台改配置、客服操作、另一个系统写同一对象；以及"用户真的会这么做吗" | —— |

代码枚举的具体做法（按端）：

- **服务端**：从范围对象的持久化类出发，grep 它的全部 setter / save / update / delete 调用点 → 这就是**写入点**全集；
  同理 grep 查询方法 → **读取点**全集。每个写入点向上追到接口，接口就是原子的入口。
- **客户端**：从页面类出发，列出所有事件回调和生命周期回调；列出所有网络请求调用点；
  找出对卡片/模型内存对象赋值的所有位置（SSE 帧合并、历史还原、本地状态切换）——这些是**端内存写入点**。
- **跨端**：三端各做一遍，读写集不同的端要拆成不同原子（或在 `ends` 中注明差异），否则多端不一致类缺陷看不见。

## 4. 覆盖闭环：用可计算的缺口代替头脑风暴

"覆盖度够不够"不靠感觉，靠下面的缺口逐条给出结论。前七项由 `scripts/op_matrix.py` 自动计算（与 pairs.md 第 1 节一一对应），
最后一项人工核对：

| 缺口 | 含义 | 结论只能是 | 性质 |
|---|---|---|---|
| **孤儿写入点** | 有写入代码，但没有任何原子会触发它 | 补一个原子，或判定为非用户触发/死代码（死代码写一条发现） | 过程门槛 |
| **孤儿读取点** | 有读取代码，但没有原子会走到 | 通常漏了"读"类动作：重进、刷新、另一端查看 | 过程门槛 |
| **空原子** | 原子没映射到任何读写点 | 补映射，或移出范围 | 过程门槛 |
| **读写集完全相同的原子** | 两个原子对共享状态是同一个动作 | 标 `represented_by` 折叠；读写集不同却标了代表的会被报出 | 过程门槛 |
| **缺少层信息的读写点** | 没写 `layer` / `layers` | 补上；否则该点的 RACE / LAYER 判定被静默跳过 | 过程门槛 |
| **替换型原子漏写的字段** | `replaces` 的原子没重写实体的某些字段 | 逐个判定"本应重置"还是"有意保留"；前者直接成为缺陷候选 | **缺陷候选** |
| **隐式动作未作答或答案无效** | 清单项没作答，或答案既没引用已有原子 id、也不是 `N/A: 理由` | 逐项作答；"不适用"必须写理由（例如"切后台不取消 SSE，读写集与不操作相同，已核对生命周期回调"） | 过程门槛 |
| **需求交互未映射**（人工核对） | 需求/设计稿里的某个交互在原子表里找不到 | 补原子；若代码里确实没有入口，这就是一条"需求未实现"发现 | 过程门槛 |

"过程门槛"类缺口要清零或有书面结论才能进入组合阶段；"缺陷候选"不需要清零，它们是阶段 4 的输入。

**最硬的一条是写入点覆盖**：共享状态只可能被写入点改变，所以只要每个写入点都被某个原子触达，
就不存在"会改变状态、却没有任何原子能触发"的写入。这把"读写点有没有被原子覆盖"变成了一个可以检查的有限集合问题。

但要清楚它**证明不了什么**——下面这些仍要靠需求映射和人工审阅：

- **读写点本身找没找全**。脚本只看得到已声明的点，这取决于代码可见性和 grep 的彻底程度。
  **看不见的服务（黑盒依赖）要显式记为盲区**，写进 analysis.md 的基线章节和"仍需确认"章节，不要假装覆盖了。
- **同一写入集下的不同产品语义**。两个入口触达相同的写入点、但业务含义不同（不同状态下的同一按钮），脚本会建议折叠；
  要不要拆开，是人审阅时的第 3 个问题。
- **条件写入**。一条代码路径里按条件写不同字段时，静态读写集是它们的并集；条件分支要拆成不同原子或写进 `stages`。
- **不写状态、只影响时序的动作**（等待、并发触发）。它们没有独立写入点，只能靠隐式清单和时间轴组合补上。

## 5. 人与 agent 的分工

**agent 负责穷举，人负责裁剪和补盲。** 不要让人从零拆原子——人的记忆天然偏向主流程，隐式动作和异常入口正是人最容易漏的。

| 步骤 | 谁来做 | 产物 |
|---|---|---|
| 从代码枚举读写点和入口 | agent | atoms.json 的 write_points / read_points |
| 从需求、设计稿、隐式清单补原子 | agent | atoms.json 的 atoms / implicit_checklist |
| 跑覆盖检查、消除缺口 | agent | pairs.md 第 1 节全部清零或有结论 |
| **审阅原子表**（HITL 检查点） | 人 | 确认或修改后的 atoms.md |

人审阅时只需要回答三个问题，并把答案写回 atoms.md：

1. **有没有代码之外的动作？**（后台、客服、其他系统、另一个角色）
2. **有没有"用户不会这么做"的原子？**（可以降级，但不要删——删了覆盖检查会报孤儿写入点）
3. **有没有应该拆开的变体？**（同一按钮在不同状态下业务含义不同）

这一步是整个流程里**唯一必须等人确认**的检查点：原子表错了，后面全部白做；原子表对了，后面的组合、剪枝、排序都是机械的。

## 6. atoms.json 结构

```json
{
  "feature": "功能名",
  "scope_object": "范围锚点对象的一句话定义",
  "write_points": [
    {"id": "W01", "field": "msg.content", "layers": {"redis": "sync", "hbase": "async"}, "where": "类#方法：说明"},
    {"id": "W02", "field": "mem.card", "layer": "client", "mode": "sync", "where": "..."}
  ],
  "read_points": [
    {"id": "R01", "field": "msg.content", "layer": "hbase", "where": "类#方法：说明"}
  ],
  "atoms": [
    {
      "id": "A0", "name": "带图提问",
      "sources": ["code", "prd"], "ends": ["android", "ios", "harmony"],
      "entry": "接口或回调",
      "writes": ["W01", "W02"], "reads": [],
      "creates_scope": true,
      "stages": ["深度思考输出中", "正文输出中"]
    },
    {"id": "A2", "name": "重新生成", "writes": ["..."], "reads": ["..."], "replaces": ["msg"]},
    {"id": "A2b", "name": "跳过深度思考", "writes": ["..."], "reads": ["..."], "represented_by": "A2"}
  ],
  "implicit_checklist": {
    "退出页面再重进": "A3",
    "切后台再回前台": "N/A: 理由"
  }
}
```

字段约定：

- **`field`** 用 `实体.字段` 命名，实体是第一段（`msg`、`mem`、`regenCache`）。同一字段在不同层是不同读写点，但 `field` 保持一致。
- **`layers` / `layer` + `mode`**：写入点二选一。同一次写入对多层的同步性不同（Redis 同步 + HBase 异步）时用 `layers`。
- **`creates_scope`**：创建范围对象的那个原子（首次提问、下单）。它只能排第一，脚本据此剔除不可能的顺序。
- **`replaces`**：语义上"产出该实体新版本"的原子（重新生成、覆盖提交、重新上传）。脚本会列出它**没有重写**的该实体字段——
  每一个都要判定"本应重置"还是"有意保留"。这条检查单独就能发现"新版本上挂着旧状态"这一整类缺陷。
- **`represented_by`**：读写集与另一原子完全相同的变体。组合时由代表出现；变体本身的入口可见性仍要在用例里单测。
- **`stages`**：会被中途打断的原子（流式输出、多步提交、长任务），逐阶段追踪中断后的落盘状态。
- **`sources`**：`code` / `prd` / `design` / `implicit` / `human`。只有 `code` 没有 `prd` 的原子值得多看一眼（产品没定义的行为）；
  只有 `prd` 没有 `code` 的原子就是"需求未实现"。
- **`implicit_checklist`**：键必须与脚本内置清单（`op_matrix.py` 的 `IMPLICIT_ACTIONS`）**原文一致**，改写过的键会被当成自定义项，
  对应的内置项判为未作答。答案有效的条件：引用至少一个已有原子 id（可以附说明，如 `"A5（regenCache 5min）"`），
  或写 `N/A: 理由`；不存在的原子 id、没有理由的 `N/A`、不含原子 id 的自由文本都判为无效。

必填与校验：读写点必须有 `id`、`field`，原子必须有 `id`、`name`，id 不能重复；原子引用不存在的读写点、
`represented_by` 指向不存在的原子或指向另一个变体（含互指、自指）都是结构错误，脚本返回 1。

以下字段只供 atoms.md / analysis.md 使用，脚本不读：`scope_object`、`sources`、`ends`、`entry`、`notes`、`where`（`where` 只原样输出）。
读取点目前只支持单个 `layer`；同一次读取回源多层（先查缓存再查库）时，拆成多个读取点。

## 7. 常见拆分错误

- **只拆了 UI 上看得见的按钮**：退出重进、等待超时这类隐式动作恰恰是高发区。隐式清单逐项作答就是为了堵这个口子。
- **忘了端内存是一层存储**：客户端内存里的对象（卡片模型、待提交的快照）有自己的写入点（SSE 帧合并、历史还原），
  很多"会话内正常、重进后出错"的问题就是内存和服务端两层的差异。
- **把多端当成一个原子**：三端读写集不同时（例如只有两端在页面销毁时回写半截内容），必须拆开或注明。
- **写入点只记了"写哪个字段"，没记"同步还是异步"**：异步窗口类缺陷全靠这一个属性。
- **没给重新生成类动作标 `replaces`**：脚本就无法发现"替换不完整"，而这一类恰恰是最隐蔽的——页面看起来完全正常。
