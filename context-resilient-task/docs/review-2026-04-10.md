## 2. 真实案例暴露的深层设计缺陷

### 2.1 task_state.md 失控膨胀 — 最严重的实战问题

**实测数据：**

| 指标 | 实际值 | 规范限制 |
|---|---|---|
| task_state.md 总行数 | **2896 行** | 300 行 |
| "Latest Stable Conclusions" 章节 | **1984 行** (L60-L2044) | 不存在此章节 |
| Active Todos 位置 | **第 2213 行** | 应在前 50 行内 |
| Active Todos 段大小 | **168 行**（16 个 todo，每个含 5-20 行子描述） | 简洁列表 |
| Completed Items 段大小 | **510 行** | 简洁列表 |
| 归档前版本 | **4025 行**（比当前版更大） | — |

**根因分析：**

1. **"Latest Stable Conclusions" 成为无控制增长的巨型章节。** Skill 规定 task_state.md "in-place edit, never append"，但 agents 面对持续产出的稳定决策/结论，自然地在此章节追加内容。这不是 agent 不遵守规范，而是 **skill 没有为"稳定结论/决策"设计归档出口**。`decisions.md` 被定义为 Tier 2 可选文件，但实际上它是刚需。

2. **task_state.md 承担了过多职责。** 当前文件同时承担：当前状态 + 决策历史 + 待办管理 + 完成记录 + scope 约束 + commit 锚点。这些关注点本应分离。

3. **300 行压缩规则无法执行。** Skill 说"超过 300 行时压缩"，但 agents 无法判断哪些内容可以安全丢弃，因为每条"Latest Stable Conclusions"都可能被后续 recovery 引用。

**直接后果 — 待办项遗忘：**
- Active Todos 在第 2213 行（文件的 76% 处）
- Agent 在 recovery 时受 context window 限制，很可能只读到文件前部分
- Agent 看不到 Active Todos，于是在"Latest Stable Conclusions"中重新记录自己理解的任务列表
- 形成事实上的**两份待办列表**，导致用户报告的"agent 遗忘历史待办项"问题

**修复方向：**
- **Active Todos 必须放在文件头部**（Goal 之后、其他章节之前），确保 recovery 时最先被读到
- **引入 decisions.md 为必需文件（提升到 Tier 1）**，"Latest Stable Conclusions"类内容归档到此
- **task_state.md 的模板需要严格固定章节顺序和最大行数**，超出部分自动归档到 progress.md / decisions.md
- **verify_mrs.py 应检查文件行数**，超过阈值时报 WARNING

### 2.2 snapshot.md 变成了 append-only 日志

**实测数据：**

| 指标 | 实际值 | 规范预期 |
|---|---|---|
| 总行数 | **1156 行** | ~50-100 行 |
| "## Context" 段数 | **18 个** | 1 个 |
| 文件行为 | append-only | 覆写（archive previous） |

**根因分析：**

Skill 规定 snapshot.md 应"覆写（archive previous with --archive）"，但 agents 在实际使用中选择追加而非覆写。原因：
1. Agent 不想丢失信息，追加比覆写更"安全"
2. Skill 没有在模板中加入"覆写确认"的格式化约束
3. `generate_snapshot.py` 脚本确实会覆写，但 agents 更多是手动编辑而非调用脚本

**修复方向：**
- snapshot.md 的模板应在文件头部加入明确指令：`<!-- OVERWRITE THIS FILE ON EACH UPDATE. Archive previous version first. -->`
- 或者改为脚本驱动的自动化流程，减少 agent 手动编辑 snapshot 的机会

### 2.3 plan.md 的 Plan Registry 边界模糊

**实测数据：**

plan.md 的 Plan Registry（L102-L169）中注册了 **78 个条目**，其中混入了：
- `CLAUDE.md` — 项目配置文件，不是计划
- `AGENTS.md` — agent 执行说明，不是计划
- `.task-state/task_state.md` — MRS 文件自身
- `.task-state/snapshot.md` — MRS 文件自身
- `.task-state/findings.md` — MRS 文件自身
- `.task-state/progress.md` — MRS 文件自身
- `.task-state/architecture.md` — MRS 文件自身
- `docs/runbooks/*.md` — 运维手册，不是计划

**根因分析：**

Skill 定义 Plan Registry 为"tracks every file produced by writing-plans/brainstorming under docs/plans/"，但没有明确的**排除规则**。Agent 在初始化时把所有相关文件都注册进去，导致 registry 失去了精确索引的意义。

**修复方向：**
- Plan Registry 应严格限定为 `docs/plans/*.md` 路径下的文件
- 其他参考文件（CLAUDE.md, AGENTS.md, runbooks 等）应放在独立的 "Reference Index" 章节
- MRS 文件自身绝不应出现在 Plan Registry 中

### 2.4 task_state.md 与 progress.md 的职责分离在实战中失败

**实测对比：**

| 维度 | task_state.md 实际行为 | progress.md 实际行为 |
|---|---|---|
| 行数 | 2896 行 | 4850 行 |
| 更新方式 | 大量追加（尤其 Latest Stable Conclusions） | append-only ✓ |
| 内容重叠 | 包含详细的验证结果、测试输出、代码审查结论 | 包含同样的验证结果、测试输出 |
| 独特价值 | Active Todos + Completed Items | 时间线 |

**根因分析：**

两个文件的内容高度重叠。Agent 在完成一个动作后，既在 progress.md 追加了记录，又在 task_state.md 的"Latest Stable Conclusions"中记录了同样（甚至更详细）的信息。

**本质问题：** Skill 的设计假设是 task_state.md 只维护"当前快照"而 progress.md 维护"完整历史"。但在实践中，agent 需要在 task_state.md 中保留足够的上下文来支撑下次 recovery，这自然导致 task_state.md 承担了部分"历史"职责。

**修复方向：**
- task_state.md 模板应强制只包含**固定长度的摘要字段**，不允许自由追加段落
- "Latest Stable Conclusions"这类开放式章节应改为 decisions.md 或 findings.md 的职责
- 每个 todo 项应限制为单行描述（不含子列表），详细上下文引用到 plan 文件或 decisions.md

### 2.5 双 Agent 协作下 MRS 规范遵守不一致

**观察：**
- task_state.md 的 "Updated By" 显示 Codex
- progress.md 的条目风格表明 Claude Code 也在更新
- snapshot.md 的 18 段追加可能来自不同 agent 的不同会话

**问题：** Skill 没有为多 agent 协作场景提供指导：
- 多个 agent 同时更新 MRS 时的冲突处理
- 不同 agent 对"in-place edit"vs "append"的理解差异
- 缺少"谁最后更新了什么"的 audit trail

## 5. 设计决策分析

### 5.1 是否需要专用待办清单文档（todos.md）？

**结论：不需要。** 待办项保留在 task_state.md 中，但上移到头部。

**分析：**
- 待办遗忘的根因不是"待办放错了文件"，而是 task_state.md 膨胀（2896 行）导致 agent 读不到尾部的 Active Todos（第 2213 行）
- 膨胀的罪魁祸首是"Latest Stable Conclusions"章节（1984 行），属于决策历史，应归档到 decisions.md
- 拆出独立 todos.md 的风险：Tier 0 从 3 个变 4 个，增加同步负担；agent 可能在两个文件中都写待办，反而更混乱
- 更好的方案：**把决策历史移出去**（decisions.md 升 Tier 1），而非把待办移出去

**方案：**
1. Active Todos 上移到 task_state.md 头部（紧跟 Status 之后）
2. decisions.md 承接"Latest Stable Conclusions"类内容，**条件性提升为 Tier 1**：multi-session / multi-agent / >10 phases 时必需，普通小任务仍可选（Codex review 反馈：一刀切升必需会增加初始化负担）
3. task_state.md 新模板固定章节顺序：

```markdown
# Task State
**Last Updated:** ...
## Goal
## Status
## Active Todos          ← 头部第一优先读到
## Current Phase
## Next Action
## Completed Items       ← 精简单行
## Open Questions
## Project Context       ← 可选，固定内容
```

### 5.2 是否需要支持 CLAUDE.md / AGENTS.md 索引？

**结论：不需要额外索引，但需要在 Plan Registry 中明确排除。**

**分析：**
- CaseGeneratorV2 的 Plan Registry 混入了 CLAUDE.md、AGENTS.md、MRS 自身文件等（plan.md:162-169）
- 根因是 Plan Registry 没有明确的排除边界，agent 把"recovery 时有用"的文件都注册了进去
- 但 CLAUDE.md 和 AGENTS.md 是 agent 启动时自动加载的先验知识，不需要 MRS 索引
- MRS 文件自身更不应该出现在 Plan Registry 中（循环引用）

**方案：**
1. Plan Registry 加入严格限定规则：

```
Plan Registry 仅注册 docs/plans/*.md 下的计划文件。
不得注册：
- CLAUDE.md / AGENTS.md（agent 自动加载）
- .task-state/* 下的 MRS 文件自身
- docs/runbooks/*（运维手册，归入独立的 Runbook Index）
```

2. task_state.md 模板增加固定的 "Project Context" 单行（可选，不会膨胀）：

```markdown
## Project Context
See CLAUDE.md for constraints, AGENTS.md for agent guidelines.
```

3. plan.md 可增加独立的 "Reference Index" 章节（与 Plan Registry 分离），用于索引 runbooks 等非计划参考文件。

### 5.3 Codex 兼容性

**问题：** Codex 在 skill 仓库中会使用 skills，但在普通项目仓库中更依赖 AGENTS.md，不会天然知道 skill 规则。当前 MRS 规则完全绑定在 SKILL.md 体系中，普通项目中的 Codex 无法获取。

**CaseGeneratorV2 实证：**
- task_state.md 的 "Updated By: Codex" 证明 Codex 在更新 MRS
- 但 snapshot.md 的 18 段追加和 task_state.md 的膨胀表明 Codex 没有遵守核心规则

**三层兼容方案：**

**层 1: MRS 文件格式保持 agent-agnostic**（已基本满足）
- 纯 Markdown + Python 脚本，不依赖特定 agent 的工具
- recovery-workflow.md 中使用通用描述"读取文件内容"而非 `cat` / `Read`

**层 2: 提供可嵌入 AGENTS.md 的精简版 MRS 规则**（新增）
- 在 `references/` 中增加 `agents-md-snippet.md`
- 约 20 行精简规则，涵盖：文件职责、待办项规则、更新规则
- **SKILL.md 中必须明确指示："初始化 MRS 时，将此 snippet 复制到项目根 AGENTS.md"**，否则 Codex 不会自动读取 skill 的 references 文件
- 用户可直接复制到项目的 AGENTS.md 中，让 Codex 也能遵守

示例内容：
```markdown
## MRS 操作规范 (.task-state/)
- task_state.md — 当前状态，原地修改，不追加。限 300 行。Active Todos 在头部。
- progress.md — 执行日志，仅追加，不覆写。
- snapshot.md — 最新快照，每次覆写整个文件，不追加段落。
- decisions.md — 稳定决策/结论，追加记录。
- plan.md — 任务计划 + Plan Registry（仅 docs/plans/*.md）。
- 待办：Active Todos 是唯一真相源。完成 = 从 Active 删除 + 追加到 Completed。
```

**层 3: verify_mrs.py 作为跨 agent 统一校验**（增强）
- 新增检查项：
  - task_state.md 行数 > 300 → WARNING（不是硬失败，Codex review 反馈）
  - snapshot.md 包含多个 `## Context` → WARNING "should be overwritten, not appended"
  - Active Todos 不在 task_state.md 前 50 行 → WARNING
  - Plan Registry 包含非 `docs/plans/` 文件 → WARNING
  - task_state.md 缺少 `Status` / `Active Todos` / `Completed Items` 段 → ERROR
- 新增 `--json` 输出模式，方便 agent 自动消费校验结果（Codex review 反馈）

## 7. 核心结论

**skill 的设计理念是对的**，但在真实长期项目（209 phases, 91 plans, 双 agent）中暴露了三个根本性弱点：

1. **task_state.md 的长度控制是文字建议而非结构约束** — 没有模板和工具层面的保证，agent 在实践中无法遵守 300 行限制。关键信息（Active Todos）被挤到文件尾部，recovery 时被截断遗忘。**修复核心：Active Todos 上移到头部 + decisions.md 承接开放式增长内容。**

2. **"in-place edit"和"append-only"的分界在持续增长的决策流面前模糊了** — 当每次会话都产生新的稳定结论时，"不追加"变成不可能的要求。**修复核心：为"稳定结论"建立独立的归档出口（decisions.md 在长任务/多 agent 场景下升 Tier 1）。**

3. **snapshot.md 的"覆写"语义没有足够的执行保障** — agent 在实践中选择更安全的"追加"而非"覆写"。**修复核心：光加注释不够，需要 verify 脚本检查 + 鼓励脚本驱动覆写。**

4. **Codex 等非 Claude 的 agent 缺乏 MRS 规范感知** — 在普通项目仓库中 Codex 不会读 skill references。**修复核心：提供 AGENTS.md snippet + SKILL.md 明确指示初始化时复制。**

5. **verify_mrs.py 校验覆盖不足且存在语义 bug** — stale snapshot 应是 WARNING 但实现为 INVALID；缺少对 Status、Active Todos、Completed Items 的检查；无 --json 输出。**修复核心：增强校验项 + 修复 stale 语义 + 支持 --json。**
