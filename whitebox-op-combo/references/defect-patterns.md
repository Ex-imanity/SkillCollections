# 缺陷模式清单

pairs.md 给出的是**候选**，这份清单告诉你每类候选在代码里该找什么。每个候选组合至少对照一遍下列模式，
把命中的模式名写进 analysis.md 对应条目，便于最后做根因收敛。

每个模式都附一个真实例子（来自 AI 搜索单条回答卡片的分析，见 `examples/ai-search-answer-card/`）。

## 目录

1. 替换不完整（字段漏更新）
2. 空值覆盖
3. 合并吞键 / 整体覆写
4. 异步窗口与读写层不对称
5. 序列化丢字段
6. 生命周期中断
7. 缓存与临时状态的 key / TTL
8. 多端实现分歧
9. 附：通用的"排除"检查

---

## 1. 替换不完整（字段漏更新）

**形态**：一个"产出新版本"的动作只重写了实体的部分字段，其余字段停留在旧版本，并被后续动作读到。

**信号**：pairs.md 第 1 节「替换型原子漏写的字段」；第 2 节 `STALE`；第 3 节三元穿透链。

**代码里找什么**：替换路径的赋值语句（常见于 update 方法里的 `peek` / `forEach` / `copyProperties`）逐字段列出来，
和实体类的字段全集做差集。重点看**命令对象（cmd / dto）里明明带着新值、落库时却没取出来**的字段——这种最常见、修起来也最便宜。

**例子**：重新生成只 `setContent` + `mergeExtData`，`mistakeMessage` 整个 JSON 快照停在旧答案。
新值其实已经被装进了 `UpdateHisMessageCmd.messageRequestList`，只是 cmd 没有对应的 getter。
页面显示新答案 B，重进后加入错题本存的是 A。另一个字段 `extData.feedback` 被 merge 保留 → 旧答案的赞"复活"并挂到新答案上。

**用例写法**：替换 → 重进（把内存态换成服务端态）→ 读该字段的动作。执行时抓历史接口，比对同源字段是否一致（见 verification.md「快速指纹」）。

## 2. 空值覆盖

**形态**：局部操作（点赞、打标）的请求里顺带回传了整条内容，服务端无条件覆盖；客户端某些路径下该内容为空串。

**信号**：`WAW`，且其中一方是局部操作。

**代码里找什么**：update 路径对每个字段的判空方式。同一段代码里 `!= null` 和 `isNotBlank` 混用是强信号——
说明作者对"空串要不要写"没有统一口径。再去客户端找该字段的兜底值（`?? ""`、默认构造的空串）。

**例子**：点赞请求带 `content`，服务端 `if (content != null) setContent(content)`；客户端 agent 卡在历史还原后 `moduleData` 为空，
以 `""` 兜底 → 点一次赞把正文写成空串，重进后卡片空白。

## 3. 合并吞键 / 整体覆写

**形态**：同一个 JSON 字段有多个写入方，有的做深合并、有的做整节点替换、有的整体覆写，后写者抹掉先写者的键。

**信号**：`WAW`，字段是 JSON / map 类型（`extData`、`attrs`、`ext`）。

**代码里找什么**：该字段的全部写入点（`scripts/op_matrix.py` 的写入点表就是清单），逐个标注合并语义：深合并 / 某个键整体替换 / 整个字段覆写。
**只要有两种以上语义并存，就是一条发现**，即使当前没有键冲突（写成"潜在"）。

**例子**：SSE 构建阶段 `extData` 整体覆写为 `{"mistakeBook":...}`；update 阶段 `mergeExtData` 对 `mistakeBook` 整节点替换、其余键深合并。
当前自洽，但任何往 SSE `extData` 加新键的迭代都会被无声抹掉。

## 4. 异步窗口与读写层不对称

**形态**：写入对某一层是异步的，另一个动作紧接着从这一层读；或者读路径查的层，写路径根本不写。

**信号**：`RACE`、`LAYER`。

**代码里找什么**：写入点用的线程池 / MQ / `@Async`；读取点查的是哪一层、有没有 fallback（Redis miss 再查 HBase）。
然后**估算窗口大小**——这决定了定级（见 verification.md）：窗口是毫秒级只在压测出现，还是秒级用户正常操作就能撞上。
再找有没有补偿机制（待更新队列、重试）以及补偿本身的 TTL。

**例子**：首轮回答 Redis 同步 + HBase 异步落库；点赞的 update 路径只查 HBase。回答结束后立即点赞 → 查不到 → 进入 30 秒 TTL 的待更新队列，
只有重新生成会消费这个队列 → 不重新生成的话，赞静默丢失。

## 5. 序列化丢字段

**形态**：内存对象上有某个状态字段，但序列化到存储时被排除，读回后这个状态不存在了。

**信号**：不会在 pairs.md 里直接出现——它表现为某个"应该有"的读取点找不到。分析中断点和降级路径时最常撞上。

**代码里找什么**：实体类上的 `@JSONField(serialize = false)`、`@JsonIgnore`、`transient`、只在 DB entity 有而在缓存 DTO 没有的字段；
以及返回给客户端的 VO 里有没有这个字段。**要检查全部存储层**，只排除了一层不算。

**例子**：`outputFinished` / `finishReason` 在 Redis（`JSON.toJSONString`）和 HBase（`JSON.toJSON` 转列）两层都被 `serialize = false` 排除，
历史 VO 也没有这个字段 → 流式输出中途退出留下的半截答案，重进后与完整答案无法区分。

## 6. 生命周期中断

**形态**：一个多阶段动作在中途被打断，已完成阶段的状态和未完成阶段的状态被不一致地落盘（或全部丢失）。

**信号**：pairs.md 第 4 节中断点。

**代码里找什么**：按"断开被谁、在哪一刻探测到"追：

1. 客户端：页面销毁回调里做了什么（取消请求？回写已渲染内容？什么都不做？）——**三端分别看**；
2. 服务端：断开在哪里被探测到（通常是下一次 `send` 抛 IOException），探测后走哪条收尾路径；
3. 收尾路径对"内容为空"和"内容不为空"是否分支——**分界线往往不在产品阶段（思考 / 正文），而在"断开那一刻缓冲区是否为空"**；
4. 用户输入（题目、图片）是和回答一起落库，还是先独立落库——前者意味着中断会把用户输入一起弄丢；
5. 协程 / 作用域：客户端的后续请求挂在页面作用域上（`viewModelScope`、页面 Task）时，页面销毁会取消它。

**例子**：深度思考阶段退出 → 缓冲区为空 → 收尾路径直接跳过落库 → 整轮问答连同用户的题图一起消失；
正文阶段退出 → 半截答案落库且被标成"已完成"，还能正常加入错题本。

## 7. 缓存与临时状态的 key / TTL

**形态**：缓存 key 的维度比它服务的对象粗（缺 questionId、缺 deviceId），不同对象互相覆盖；或 TTL 到期后路径降级。

**信号**：pairs.md 里含缓存字段的 `RAW` / `WAW`——**分值低，但不能跳过**。脚本看不出 key 的维度，只能人看。

**代码里找什么**：key 的拼接函数（是否包含对象 id、设备 id、登录态分支）；恢复时是否有守卫（仅当为空才恢复 / 校验 id 一致）；TTL 与续期逻辑；
TTL 到期后读取方拿到 null 会走哪条分支。每个带 TTL 的状态都要在隐式动作清单里有一个"等待超过 TTL"的原子。

**例子**：重新生成的图片缓存 key 只含 userId、TTL 5 分钟、只对带图提问写入 → 带图提问 Q1 后再文字提问 Q2，对 Q2 重新生成会恢复成 Q1 的图；
同账号跨设备同样串。超过 5 分钟后重新生成则读不到缓存，路由降级，错题本入口消失。

## 8. 多端实现分歧

**形态**：同一协议三端各自实现，读写集不同。

**信号**：原子表里 `ends` 注明了差异、或不得不按端拆原子。

**代码里找什么**：对每个原子，三端的请求体构造、响应合并、页面销毁行为逐项对表。**请求体里"依赖服务端缓存补齐"的字段**是重点——
某一端没带、完全依赖缓存时，缓存一失效只有这一端出问题。

**例子**：iOS 的重新生成请求只带 `regenerate` + `regenerateParam`，`sendType` / `agentType` 全靠服务端缓存；Android、鸿蒙带了 agentType →
缓存过期后 iOS 最先暴露降级。页面销毁时 Android、iOS 回写已渲染的半截内容，鸿蒙不回写。

## 9. 附：通用的"排除"检查

每条候选在判定"已确认"之前，先找它**不成立**的理由，并把排除过程写进 analysis.md：

- 看似会出问题的路径，是否被另一层兜住了？（例：会话内加入错题本读的是被 SSE 最终帧刷新过的内存，而不是服务端旧值 → 会话内路径正确，只有重进后才错）
- 开关 / 实验 / 配置是否让这条路径根本不可达？（Apollo 开关为 false 时整段 update 直接 return）
- UI 上这个顺序是否根本点不到？（重新生成按钮只在最后一张卡上 → "回到前一轮重生"不可达，真正可达的是跨题型串题）

写下排除的路径和写下确认的缺陷同样重要：它告诉读者哪些顺序已经查过、不必再测，也防止开发拿一个被兜住的场景来反驳整条结论。
