# 产物模板

所有产物落在 `whitebox-output/{slug}/`（用户指定了目录则用用户的）：

```
whitebox-output/{slug}/
├── baseline.md     ← 阶段 0：范围对象、仓库/分支/提交、配置来源、盲区
├── atoms.json      ← 阶段 1–2：读写点与原子（脚本输入，机器可读）
├── atoms.md        ← 阶段 2：原子表（人审阅用，HITL 检查点）
├── pairs.md        ← 阶段 3：op_matrix.py 输出，不手改
├── analysis.md     ← 阶段 4–5：缺陷分析
└── cases.md        ← 阶段 6：测试用例（兼容 case-lite full.md 格式）
```

## atoms.md

给人看的原子表，内容与 atoms.json 一致，但按"人要审什么"组织：

```markdown
# {功能} —— 原子动作表

范围对象：{一句话}

## 原子动作

| ID | 动作 | 入口 | 写 | 读 | 来源 | 端差异 | 备注 |
|---|---|---|---|---|---|---|---|
| A0 | 带图提问 | mainSearch（SSE） | 回答正文、错题本快照、兄弟卡片、重生缓存、端内存 | — | 代码 / 需求 | — | 创建动作；阶段：深度思考中 / 正文中 |
| A2 | 重新生成 | mainSearch + regenerate | 正文、extData.mistakeBook、兄弟卡片、端内存 | 重生缓存、HBase 记录 | 代码 / 需求 | iOS 请求体不带 agentType | 替换回答；A2b 跳过深度思考由它代表 |

## 隐式动作清单

| 动作 | 结论 |
|---|---|
| 退出页面再重进 | A3 |
| 切后台再回前台 | 不适用：{理由} |

## 覆盖检查结果

（粘贴 pairs.md 第 1 节的结论：孤儿写入点 / 孤儿读取点 / 空原子 / 替换漏写字段，每条都要有处理结论）

## 盲区

- {看不见代码的服务、无法确认的配置值}

## 请确认

1. 有没有代码之外的动作（后台、客服、其他系统、另一个角色）？
2. 有没有用户实际上不会做的原子？（会降级，不会删除）
3. 有没有应该拆开的变体？
```

## analysis.md

```markdown
# {功能} —— 代码问题分析

## 0. 分析基线

| 仓库 | 分支 | 最新提交 |
|---|---|---|

下文每条结论以上述分支为准。标【已确认】的可在代码中直接读到；标【潜在】的取决于运行期数据，需实测取证。
盲区：{黑盒服务、未知配置}

## 1. 【状态标记】{一句话说清楚：什么顺序 → 什么后果}

> 触发条件：{最常见的那条路径，一句话}

{先排除看似会出问题但实际被兜住的路径（如有）}

{因果链：每一环引用 `文件:行号`，关键处贴代码片段}

{后果表：哪些字段停在什么状态、用户在哪里能感知}

### 1.x 归属结论（服务端 / 客户端 / 协议）
{判定依据 + 最小修复点}

### 1.x 快速指纹
{不走完全部流程就能判定的信号}

## N. 优先级建议

| 级别 | 问题 | 依据 |
|---|---|---|

## N+1. 根因收敛

上述问题收敛到 **K 个结构性成因**：
1. **{成因}** —— {说明}。§a §b 源于此。建议：{结构性修复方向}

## N+2. 仍需确认的问题

1. {问题} —— {需要谁、用什么证据回答}
```

写作约定：

- 每条发现的标题就是结论，读者只看标题也能知道问题是什么。
- 引用写 `文件:行号`；在能生成可点击链接的环境里用相对路径链接。
- 结论直接写最新的；用户纠正或测试反馈后改正文，不保留推理历史。
- 根因收敛是给架构/负责人看的：把 10+ 条具体问题收敛到 3–5 个成因（缺少统一的读改写契约、状态在存储里不存在、多端各自实现同一协议……）。

## cases.md

与 case-lite 的 `full.md` 格式兼容（编号即路径），可直接用 case-lite 的 `writeback.py` 写回搬山：

```markdown
# {功能} —— 操作组合测试用例

覆盖对象：{范围对象}

| 操作 | 简称 | 接口 |
|---|---|---|

**验证分支**：{同 analysis §0}

**预期结果的口径**：所有「预期结果」写的是**产品应有行为**。凡当前实现预计不符的，在测试点末尾以 `备注：` 标注对应的 analysis.md 章节号，执行时可直接区分"用例写错"与"确实是缺陷"。

**通用环境要求**：
- {实验、开关——写明开关为 false 时哪些用例会失效}
- {抓包需要留存的字段}

## 场景1：{A 与 B 的顺序组合}

### 测试点1.1：{A → B → C 后，{字段}应为{期望}}

#### 执行步骤
1. {前置融入第一步}
2. {操作，带时间要求}

#### 预期结果
1. {UI 断言}
2. {接口字段断言}

**更快的判定方式**：{快速指纹}

备注：{当前实现与预期不符的原因一句话}，见 analysis §N。
```

用例约定：

- **场景按"组合的原子对"组织**（点赞与重新生成的顺序组合、加入错题本与退出重进的组合），另设"并发与竞态""跨端一致性""中断"等横切场景。
- **预期结果写产品应有行为**，不写"现状"。现状写在备注里并指向 analysis 章节——否则缺陷修复后用例全部要改。
- 每个测试点的步骤里写清**时间要求**和**端别**。
- 纯白盒、黑盒无法触发的边界（需要精确卡时序）单独成点，标题注明"白盒边界"。
- 不写优先级标记（与 case-lite 一致，由用户事后标注）。
